`@motherbase/client` is the official TypeScript SDK for Motherbase. Query tables with the Supabase-style `client.from(table)` builder or Prisma-style `client.db.table` methods. The same client also provides auth, storage, realtime, and edge functions.

Use **Project Studio → Connect** for the exact API URL, WebSocket URL, package name, and project ID for a project.

## Install

```bash
npm install @motherbase/client
# Optional, only when you use realtime:
npm install socket.io-client
```

## Initialize

```ts
import { createClient, localStorageStorage } from '@motherbase/client'

export const client = createClient(
  process.env.NEXT_PUBLIC_MOTHERBASE_URL!,
  process.env.NEXT_PUBLIC_MOTHERBASE_KEY,
  { storage: localStorageStorage() },
)
```

The stored session is loaded before the first request and the first channel subscribe, so there is nothing to await at startup. `await client.hydrate()` returns it if you want it yourself, with no network call.

The second argument is the project's **publishable key**, sent as an `apikey`
header. Find it on **Project Studio → Connect**. It is optional unless the project
has key enforcement turned on.

Passing a **secret** key instead (`mb_secret_...`) runs every request as
`service_role`, which bypasses row level security, and unlocks the
`client.auth.admin` namespace below. Server side only — see
[API Keys](/docs/platform/api-keys/). The SDK logs a console warning if a secret
key is used where `window` exists.

Client options — native shape:

```ts
createClient(url, key, {
  storage,            // session storage adapter, defaults to memoryStorage()
  autoRefresh: true,  // revalidate once on 401, defaults to true
  accessTokens: true, // send a JWT on REST and storage requests, defaults to true
  fetch,              // custom fetch implementation
  headers,            // extra headers for every request
  compat: 'supabase', // optional, see below
  realtimeIoFactory,  // test/custom socket.io factory
})
```

The `supabase-js` option shape is accepted too, so a ported config compiles as-is:

```ts
createClient(url, key, {
  auth: { persistSession: true, storage, storageKey, autoRefreshToken: true, detectSessionInUrl: true, flowType: 'pkce' },
  global: { headers, fetch },
  db: { schema: 'public' },
})
```

Storage precedence is `storage` → `auth.storage` → `auth.persistSession`
(`true` means localStorage, `false` means memory). `auth.flowType` is `'implicit'`
(the default) or `'pkce'`, see [Auth](#auth); `auth.debug` is accepted for signature
parity and ignored. `compat: 'supabase'` aligns the behaviours that share a supabase-js
spelling but differ (an `update()` / `delete()` matching nothing answers an empty array
instead of a `404`). `db.schema` throws for anything but `'public'`, which is the only
schema the REST layer serves tables from; call functions in another exposed schema with
`client.schema(name).rpc()`.

## Result shape

Expected API failures resolve to `{ data, error }` instead of throwing.

```ts
const { data, error } = await client.from('products').select('*').limit(20)

if (error) {
  console.error(error.message, error.status, error.code)
}
```

`error` is `null` on success. Programmer errors can still throw, for example calling unsupported realtime channel event types.

## Query builder

`client.from(table)` returns a chainable, awaitable PostgREST-style builder mapped to `/rest/v1/:model`.

```ts
const { data: products, error } = await client
  .from('products')
  .select('id,name,price')
  .eq('status', 'active')
  .in('id', ['p1', 'p2'])
  .lt('price', 50)
  .order('name', { ascending: false })
  .range(0, 9)
```

Single-row helpers:

```ts
const { data: product } = await client
  .from('products')
  .select('*')
  .eq('id', 'p1')
  .single()

const { data: maybeProduct } = await client
  .from('products')
  .select('*')
  .eq('id', 'p1')
  .maybeSingle()
```

Mutations:

```ts
await client.from('products').insert({ name: 'Tea', price: 12 })
await client.from('products').update({ price: 9 }).eq('id', 'p1')
await client.from('products').delete().eq('id', 'p1')

// INSERT .. ON CONFLICT DO UPDATE. The target defaults to the primary key.
await client.from('products').upsert({ id: 'p1', name: 'Tea' })
await client.from('products').upsert({ sku: 'T1', name: 'Tea' }, { onConflict: 'sku' })
await client.from('products').upsert(rows, { ignoreDuplicates: true })
```

Writes return no rows by default. Chain `.select()` when you need the inserted or
updated representation; the caller must also have SELECT access to receive it. Raw
REST writes default to `Prefer: return=minimal`, while `Prefer: return=representation`
requests rows explicitly. A bulk `insert`/`upsert` sends an explicit column set, so a
key missing from one row is still written as `NULL` (or as the column default under
`{ defaultToNull: false }`) rather than being inferred from the first row alone.

Two server-side rules apply to every query and will bite if you assume `supabase-js`
behaviour: an unbounded `select()` is capped at **1000 rows** by default (the operator can
lower `api.rest.maxRows`; paginate with `.range()` or pass
an explicit `.limit()`), and an unfiltered `delete()` or `update()` is refused with a `400` for
non-admin callers — deliberately, since `supabase-js` would have rewritten every visible row.

### Filters

| Group | Methods |
|---|---|
| Comparison | `eq`, `neq`, `gt`, `gte`, `lt`, `lte` |
| Pattern | `like`, `ilike`, `likeAllOf`, `likeAnyOf`, `ilikeAllOf`, `ilikeAnyOf` |
| Set / null | `in`, `is`, `match` |
| Logic | `or`, `not`, `filter` |
| Full-text | `textSearch(column, query, { type: 'plain' \| 'phrase' \| 'websearch', config })` |
| Array / range containment | `contains`, `containedBy`, `overlaps` |
| Range position | `rangeGt`, `rangeGte`, `rangeLt`, `rangeLte`, `rangeAdjacent` |

```ts
await client
  .from('posts')
  .select('*')
  .or('status.eq.live,and(price.gt.10,price.lt.20)')
  .textSearch('body', 'cat & dog', { type: 'websearch', config: 'english' })
  .contains('tags', ['news'])
  .not('archived', 'is', null)
```

### Modifiers

| Modifier | Effect |
|---|---|
| `select`, `order`, `limit`, `range` | The usual shaping. `order`, `limit` and `range` accept `{ referencedTable }` so they apply to an embedded relation rather than the parent |
| `single()`, `maybeSingle()` | One row instead of an array |
| `returns<T>()` / `overrideTypes<T>()` | Compile-time cast only |
| `abortSignal(signal)` | Cancel in flight |
| `throwOnError()` | Reject instead of resolving `{ data: null, error }` |
| `maxAffected(n)` | Refuse a write that would touch more than `n` rows (`Prefer: handling=strict, max-affected=n`) |
| `rollback()` | Run the query, then roll the transaction back (`Prefer: tx=rollback`) |
| `csv()` | `text/csv`; `data` is a string |
| `geojson()` | `application/geo+json`; `data` is the parsed object |
| `explain(options)` | The query plan. Admin session only |

```ts
// Row count without fetching rows
const { count } = await client.from('products').select('*', { count: 'exact', head: true })

// CSV instead of JSON — data is a string
const { data: csv } = await client.from('products').select('*').csv()

// Query plan. Admin session only; anyone else gets 403 PGRST103.
const { data: plan } = await client.from('products').select('*').explain({ analyze: true })

// Cancel in flight
const controller = new AbortController()
await client.from('products').select('*').abortSignal(controller.signal)

// Validate a write without persisting it
await client.from('products').update({ price: 9 }).eq('id', 'p1').rollback()

// Refuse to touch more than one row, in case the filter is wrong
await client.from('products').update({ price: 9 }).eq('id', 'p1').maxAffected(1)
```

`maxAffected` sends a `Prefer` header; a server that does not implement the
preference ignores it. It is a safety net, not a guarantee — keep the filter right.

### Prisma-style queries

`client.db.<table>` offers familiar Prisma-style methods over the **same REST API** as
`client.from()`. It does not install Prisma or connect directly to PostgreSQL.
Both styles obey the caller's RLS policies.

```ts
const products = await client.db.products.findMany({
  where: { status: 'active', price: { lt: 50 } },
  select: { id: true, name: true, price: true },
  orderBy: { name: 'asc' },
  take: 10,
})

const product = await client.db.products.create({ data: { name: 'Tea', price: 12 } })
await client.db.products.update({ where: { id: product.id }, data: { price: 9 } })
```

Unlike `from()`, these methods return rows directly and **throw on error**. Reads:
`findMany`, `findFirst`, `findFirstOrThrow`, `findUnique`, `findUniqueOrThrow`,
and `count`. Writes: `create`, `createMany`, `createManyAndReturn`, `update`,
`updateMany`, `delete`, `deleteMany`, and `upsert`. `createMany` returns
`{ count }`; `updateMany` and `deleteMany` return the affected rows.

`where` supports equality, `in`, `gt`, `gte`, `lt`, `lte`, `contains`,
`startsWith`, and `endsWith`. Conditions are combined with AND. `skip` needs
`take`. Writes require a `where` that matches at least one column, so an
accidental `{ id: undefined }` cannot update or delete the whole table.
Use `from()` for embedded relations, `or()` and other advanced filters. Views
are readable through either style, but cannot be written through the typed SDK.

### Embedding

Foreign keys are resolved in both directions, so the PostgREST embedding syntax works:

```ts
await client.from('posts').select('id,title,author(id,name)')
await client.from('posts').select('*,comments!inner(body)')
```

An embedded relation passes the same exposure and RLS checks as a top-level one.

### Database functions

`client.rpc(fn, args)` calls a Postgres function in the `public` schema and maps
to `POST /rest/v1/rpc/:fn` (or `GET`, see below). Arguments are bound by **name**,
the same way PostgREST does it, so the function is resolved from the catalog by
matching the keys of `args` against the function's parameter names — not by
position and not by arity.

```ts
const { data } = await client.rpc('search_products', { term: 'tea' })
```

What comes back depends on what the function returns, exactly as in PostgREST:
a scalar or a single composite row resolves to one value (`data` is that value,
not an array); a `setof` / `returns table` function resolves to an array, one
entry per output row.

```ts
// scalar / single row -> data is the value itself
const { data: count } = await client.rpc('count_active_products')

// setof / table -> data is an array
const { data: rows } = await client.rpc('list_products_by_tag', { tag: 'sale' })
```

#### Read-only calls (GET)

```ts
// Arguments become query parameters instead of a JSON body
await client.rpc('search_products', { term: 'tea' }, { get: true })
```

`{ head: true }` and `{ count }` are accepted for supabase-js parity, but the `/rpc/`
route does not compute a total today: `count` comes back `null`. To count a function's
result, return the count from the function itself, or call a table query with
`select('*', { count: 'exact', head: true })`.

`{ get: true }` is only valid for a function marked `STABLE` or `IMMUTABLE`.
Calling a `VOLATILE` function with `get: true` is refused with a `405` (`PGRST101`,
"Use POST") rather than silently falling back to `POST` — a `GET` is meant to be
safe to retry, cache and prefetch, and a volatile function is, by definition,
not.

#### Overloads and defaults

Postgres function overloading works by argument *names*, not arity: an overload
is selected when every key in `args` matches one of its named parameters and
every parameter without a default is present in `args`. A call that matches no
overload (an unknown function name, or a name/argument combination nothing
declares) answers `404` (`PGRST202`) rather than guessing the closest match.
`VARIADIC` parameters cannot be targeted through named arguments and are never
selectable over REST.

```ts
// defined as search_products(term text, in_stock boolean default true)
await client.rpc('search_products', { term: 'tea' })              // in_stock defaults
await client.rpc('search_products', { term: 'tea', in_stock: false })
```

#### Whole body as one argument

The REST layer also understands `Prefer: params=single-object`, PostgREST's
header for sending the entire body as one JSON value rather than binding each
key to a named parameter. It only works against a function declared with a
single `json`/`jsonb` parameter. `client.rpc()` does not set this header today —
reach for it only when calling the REST endpoint directly.

#### Calling functions in another schema

`public` is the default and the only schema `from()` reads tables from, but a
function in another **exposed** schema is reachable with `client.schema(name)`:

```ts
// pgmq_public is exposed when the Queues feature is enabled
await client.schema('pgmq_public').rpc('pop', { queue_name: 'emails' })
```

Requesting a schema that isn't on the exposed list answers `406` (`PGRST106`)
naming the schemas that are, instead of silently serving `public` under a
different name.

#### Security: `SECURITY DEFINER` functions are refused by default

A `SECURITY DEFINER` function runs as its *owner*, not as the caller, and row
level security does not apply to a table's owner unless that table is
`FORCE ROW LEVEL SECURITY`. Exposing one over REST by default would hand every
caller — including `anon` — a path around every RLS policy in the database. So
the server refuses to call a `SECURITY DEFINER` function (`403`, `PGRST203`)
until an operator explicitly allowlists it by name in the **API · REST** settings
group, field **Exposed SECURITY DEFINER functions** (`api.rest.rpcSecurityDefiner`,
seeded from `REST_RPC_SECURITY_DEFINER`; see the [settings reference](/docs/reference/settings/#api--rest)).
Function names are matched verbatim against
`pg_proc.proname`, so an unquoted `CREATE FUNCTION` (lower-cased by Postgres) and
a quoted, case-sensitive one are allowlisted differently.

<Warning>
Allowlisting a `SECURITY DEFINER` function means every caller who can reach
`/rest/v1/rpc/<name>` — including an anonymous one, unless you gate it another
way — runs it with the owner's privileges. Treat the allowlist the same way
you'd treat a new admin-only route, not a toggle.
</Warning>

#### Typed functions

With a generated `Database` type, `.rpc()` reads the function's argument and
return types from `Functions`, so both the call and `data` are checked at
compile time:

```ts
import type { Database } from './database.types'

const client = createClient<Database>(url, anonKey)
const { data } = await client.rpc('search_products', { term: 'tea' })
// data is typed from Functions['search_products']['Returns']
```

| Error | HTTP | Meaning |
|---|---|---|
| `PGRST202` | 404 | No function with that name and those argument names exists in the schema cache |
| `PGRST203` | 403 | A `SECURITY DEFINER` function exists but isn't allowlisted |
| `PGRST101` | 405 | A `VOLATILE` function was called with `{ get: true }` |
| `PGRST106` | 406 | The requested schema isn't `public` or an exposed optional schema |

### Transactions

```ts
const { data, error } = await client.transaction(tx => {
  tx.from('orders').insert({ id, total })
  tx.from('stock').update({ count: 4 }).eq('sku', sku)
})
```

All or nothing: one Postgres transaction for the whole callback. supabase-js has no
equivalent — the usual workaround is a sequence of awaited writes inside a `try`, which is
not a rollback, because whatever already committed stays committed.

The callback **awaits nothing**. It describes the writes; they are sent together and applied
together. `data` is one result array per operation, in declaration order.

- Writes only (`insert`, `upsert`, `update`, `delete`). A read throws before anything is sent.
- An empty callback throws.
- 100 operations maximum, enforced server side.
- The whole batch runs as one caller, so two operations can never run as different users.

Wire format: [`POST /rest/v1/batch`](/docs/reference/rest-api/).

### Typed clients

Pass the type generated by `motherbase gen types typescript` to type both
`from()` and `db`: table names, columns, rows, and writes get autocomplete and
type checks. `.rpc()` reads its argument and return types from `Functions`:

```ts
import type { Database } from './database.types'

const client = createClient<Database>(url, anonKey)
const { data } = await client.from('products').select('id,name')  // data: { id: string; name: string }[]
const products = await client.db.products.findMany({ select: { id: true, name: true } })
```

Without a `Database` type the client behaves exactly as it does untyped. See the
[CLI reference](/docs/cli/commands/).

<Note>
REST queries are enforced by PostgreSQL RLS. A signed-out request runs as `anon`; a signed-in request runs as `authenticated` with `auth.uid()` and `auth.jwt()` claims.
</Note>

## Auth

`client.auth` **is** [Better Auth](https://www.better-auth.com/docs)'s own client,
typed with every plugin the server mounts (anonymous, email OTP, magic link, phone
number, two-factor, organization, generic OAuth, JWT, passkey, SSO, API keys) and
shipped as a dependency of `@motherbase/client`: you do not install `better-auth`
yourself. Every method in Better Auth's documentation is there under its own name and
parameters, and resolves to Better Auth's `{ data, error }`.

This is a deliberate break with supabase-js (since `@motherbase/client` 2.0): the
`signInWithPassword` / `mfa` names are gone. Porting is a rename, and the
[compatibility matrix](#compatibility-matrix) names the Better Auth call for every
supabase-js one. `motherbase migrate codemod` lists them in your code.

```ts
await client.auth.signUp.email({ email: 'user@example.com', password: 'secret123', name: 'Alice' })

const { data, error } = await client.auth.signIn.email({
  email: 'user@example.com',
  password: 'your-password',
})

// Asks the server: the verified read. { session, user }, or null.
const { data: current } = await client.auth.getSession()

// The stored session, no network call. Display only, never authorize on it.
const stored = await client.hydrate()

await client.auth.signOut()
```

`signUp.email` answers `{ token, user }`, with a `null` token while the project requires
email verification first. A plugin turned off in the project settings keeps its methods
on the client, typed, and the server answers them with a `404`.

Email OTP and password reset:

```ts
await client.auth.emailOtp.sendVerificationOtp({ email, type: 'sign-in' })
await client.auth.signIn.emailOtp({ email, otp: '123456' })

// The reset is completed with a one-time code, not a redirect link
await client.auth.emailOtp.requestPasswordReset({ email })
await client.auth.emailOtp.resetPassword({ email, otp: '123456', password: 'new-secret' })

// Magic link and SMS, when those plugins are on
await client.auth.signIn.magicLink({ email, callbackURL: 'https://app.example.com/' })
await client.auth.phoneNumber.sendOtp({ phoneNumber: '+33600000000' })
await client.auth.phoneNumber.verify({ phoneNumber: '+33600000000', code: '123456' })
```

Social sign-in (OAuth):

```ts
// Navigates the browser to the server's start route, which redirects on to the provider
await client.auth.signIn.social({
  provider: 'google',
  callbackURL: 'https://app.example.com/auth/callback',
})

// On the callback page. createClient already does this on load
// unless auth.detectSessionInUrl is false.
const { data, error } = await client.auth.getSessionFromUrl()
```

In a browser, `signIn.social` is a full-page navigation rather than a fetch: the server
sets its OAuth state cookie there, and a cookie set on a cross-site fetch response is
dropped by Safari, Firefox and Chrome incognito. Pass `disableRedirect: true` to get the
URL back instead. `callbackURL` must be a trusted origin. `getSessionFromUrl()` resolves
`{ data: null, error: null }` when the URL carries no token, so it is safe on every page.

With `createClient(url, key, { auth: { flowType: 'pkce' } })` the redirect comes back with
`?code=` instead of a `#access_token=` fragment, and the client exchanges it on load
(or through `client.auth.exchangeCodeForSession(code)`) against the verifier this browser
kept, so a leaked redirect URL is worth nothing on its own.

Native apps hand over the provider's id token directly (Sign in with Apple, Google One Tap):

```ts
await client.auth.signIn.social({ provider: 'apple', idToken: { token, nonce } })
```

Account management:

```ts
// Profile fields are flat, not under `data`. `name` is derived: once `firstName`
// or `lastName` is set it reads "firstName lastName", and a `name` sent alone
// over them is refused with a 400.
await client.auth.updateUser({ firstName: 'Ada', lastName: 'Lovelace', image: url })

await client.auth.changePassword({ currentPassword: 'old-secret', newPassword: 'new-secret' })

// Where Better Auth's changeEmail / changePassword cannot: an anonymous user's first
// email (which makes it permanent, keeping its id), a first password, or a password
// replaced with the one-time nonce reauthenticate() emails.
await client.auth.reauthenticate()
await client.auth.updateUserCredentials({ password: 'new-secret', nonce: '123456' })

// Sessions per device
await client.auth.listSessions()
await client.auth.revokeSession({ token })
await client.auth.revokeOtherSessions()

// Self-service account deletion: the password, or a fresh session
await client.auth.deleteUser({ password })
```

Auth state listener:

```ts
const { data: { subscription } } = client.auth.onAuthStateChange((event, session) => {
  // event: 'INITIAL_SESSION' | 'SIGNED_IN' | 'USER_UPDATED'
  //      | 'MFA_CHALLENGE_VERIFIED' | 'SIGNED_OUT'
})
```

`INITIAL_SESSION` fires once, as soon as the stored session has been read and before any
other event — asynchronously, so unsubscribing synchronously suppresses it, exactly as in
supabase-js. It is what the standard bootstrap
(`if (event === 'INITIAL_SESSION') setLoading(false)`) depends on: a signed-out visitor
produces no other event, so without it the app renders its loading state forever. There is
no `TOKEN_REFRESHED`: Better Auth sessions are not rotated.

Every `client.auth` call that creates, replaces or ends the session writes it back to the
SDK's session store, so `from()`, storage, functions and realtime use the same session. `from()`
and storage send a short-lived JWT minted from it once one is ready (see
[Access tokens in the SDK](/docs/platform/auth/#access-tokens-in-the-sdk)).
Calls that change the user without returning it (`updateUser`, `changeEmail`,
`updateUserCredentials`, `twoFactor.disable`) are followed by a session read, so the stored
user and `USER_UPDATED` follow. On a `401` the SDK revalidates once against
`/api/auth/get-session` (concurrent requests share one revalidation); if the session is gone
it clears local state and emits `SIGNED_OUT`. There is no refresh token to rotate.

The supabase-js spellings stay on the session the SDK stores (`client.hydrate()`,
`onAuthStateChange`): `access_token`, `refresh_token` (always `null`), `token_type`, and on
the user `user_metadata`, `email_confirmed_at`, `identities` and the rest. Better Auth's own
responses keep its native shape.

### Two-factor

```ts
// Returns the otpauth URI (render it as a QR code) and the backup codes. Shown once.
const { data } = await client.auth.twoFactor.enable({ password })
await client.auth.twoFactor.verifyTotp({ code: '123456' })   // confirms enrolment

await client.auth.twoFactor.getTotpUri({ password })
await client.auth.twoFactor.generateBackupCodes({ password })
await client.auth.twoFactor.disable({ password })
```

When the account has a second factor, password sign-in answers
`{ twoFactorRedirect: true, twoFactorMethods }` and stores no session until a code is
verified:

```ts
const { data } = await client.auth.signIn.email({ email, password })

if (data && 'twoFactorRedirect' in data) {
  await client.auth.twoFactor.verifyTotp({ code, trustDevice: true })

  // Or a code by email / SMS:
  await client.auth.twoFactor.sendOtp()
  await client.auth.twoFactor.verifyOtp({ code })

  // Or a recovery code:
  await client.auth.twoFactor.verifyBackupCode({ code })
}
// The verified session is stored; onAuthStateChange reports MFA_CHALLENGE_VERIFIED.
```

The SDK sends the pending-challenge cookie on these calls, so the project's CORS settings
must allow the app's origin when app and API are on different sites. Enabling two-factor
requires the password: Better Auth treats it as a credential change. There is one TOTP
factor per user, not a factor list.

### Passkeys

```ts
await client.auth.passkey.addPasskey({ name: 'MacBook' })
await client.auth.passkey.listUserPasskeys()
await client.auth.passkey.updatePasskey({ id, name: 'Work laptop' })
await client.auth.passkey.deletePasskey({ id })

await client.auth.signIn.passkey()
```

The project needs **Auth · Passkey** on, with the relying party set to the app's domain.

### Enterprise SSO

```ts
await client.auth.signIn.sso({ email, callbackURL })
await client.auth.signIn.sso({ domain: 'acme.com', callbackURL })
await client.auth.signIn.sso({ providerId: 'acme-okta', callbackURL })
await client.auth.signIn.sso({ organizationSlug: 'acme', callbackURL })
```

Resolves the identity provider and redirects to it. The project needs the SSO plugin
enabled and at least one provider registered (Studio → Authentication → Organizations,
with the project-wide **Auth · SSO** switch enabled).

### Organizations, invitations and teams

```ts
const { data: organization, error } = await client.auth.organization.create({
  name: 'Acme',
  slug: 'acme',
})

await client.auth.organization.inviteMember({
  organizationId: organization!.id,
  email: 'person@acme.example',
  role: 'member',
})

const { data: full } = await client.auth.organization.getFullOrganization({
  query: { organizationId: organization!.id },
})
```

The namespace is Better Auth's organization client:

| Capability | Methods |
|---|---|
| Organization lifecycle | `create`, `update`, `delete`, `list`, `getFullOrganization`, `setActive`, `checkSlug`, `leave` |
| Members and permissions | `listMembers`, `getActiveMember`, `getActiveMemberRole`, `removeMember`, `updateMemberRole`, `hasPermission` |
| Invitations | `inviteMember`, `acceptInvitation`, `rejectInvitation`, `cancelInvitation`, `getInvitation`, `listInvitations`, `listUserInvitations` |
| Teams | `createTeam`, `updateTeam`, `removeTeam`, `listTeams`, `setActiveTeam`, `listUserTeams`, `listTeamMembers`, `addTeamMember`, `removeTeamMember` |

`organizationId` is optional on methods that target an organization and defaults
to the active organization in the session. `create` activates the new
organization unless `keepCurrentActiveOrganization` is true. Teams require
`auth.organization.teamsEnabled`; the available roles are `owner`, `admin` and
`member`. `auth.organization.maxMembers` is `0` for unlimited seats and applies
to direct member adds, invitation acceptance and SSO auto-provisioning.

Invitations are email-based. The invitation email contains the invitation id;
the recipient can inspect it with `getInvitation({ query: { id } })`, then call
`acceptInvitation({ invitationId })` or `rejectInvitation({ invitationId })`.
An organization admin can withdraw an outgoing invitation with
`cancelInvitation({ invitationId })`.

For authorization checks, use `hasPermission({ permissions })` or handle the
structured error returned by a refused operation. Do not infer permissions from
the fact that a caller is an organization member.

### Runtime SSO provider management

Organization SSO providers are tenant data. The project must have **Auth · SSO**
enabled, and an organization provider must include that organization's
`organizationId`:

```ts
const { data, error } = await client.auth.sso.register({
  providerId: 'acme-okta',
  issuer: 'https://acme.okta.com',
  domain: 'acme.example',
  organizationId: organization.id,
  oidcConfig: {
    clientId: '…',
    clientSecret: '…',
    discoveryEndpoint: 'https://acme.okta.com/.well-known/openid-configuration',
    scopes: ['openid', 'email', 'profile'],
  },
})
```

Use `samlConfig` instead of `oidcConfig` for SAML. The returned `redirectURI` is
the callback URL to register at the IdP. `sso.providers()` and `sso.getProvider()`
mask or omit secrets; `sso.updateProvider()` merges the supplied config fields and
`sso.deleteProvider()` removes one. Only an organization owner or admin may manage a
provider scoped to that organization. A provider without `organizationId` is
project-wide.

### User administration

`client.auth.admin` is Motherbase's API, shaped like `supabase.auth.admin` — not Better
Auth's admin plugin, which the server does not mount. It requires a **secret** key, so it
belongs on a server. A publishable key gets a 401 from these routes.

```ts
const admin = createClient(API_URL, process.env.MOTHERBASE_SECRET_KEY!)

await admin.auth.admin.listUsers({ page: 1, perPage: 50 })
await admin.auth.admin.getUserById(id)
await admin.auth.admin.createUser({ email, password, role: 'USER' })
await admin.auth.admin.updateUserById(id, { role: 'ADMIN', password })
await admin.auth.admin.signOut(id)              // ends every session they hold
await admin.auth.admin.deleteUser(id)
await admin.auth.admin.inviteUserByEmail(email)
await admin.auth.admin.mfa.listFactors({ userId: id })
await admin.auth.admin.mfa.deleteFactor({ userId: id, id: factorId })
```

`generateLink({ type, email })` covers `signup`, `invite`, `magiclink` and `recovery`.
Recovery is code-based, so it returns `email_otp` and no `action_link`; the

## Storage

```ts
const bucket = client.storage.from('avatars')

const { data: uploaded, error } = await bucket.upload('me.png', file, {
  visibility: 'public',
})

if (!error && uploaded) {
  const { data: blob } = await bucket.download(uploaded.path)
  const { data: signed } = await bucket.createSignedUrl(uploaded.path, 3600)
  const { data: pub } = bucket.getPublicUrl(uploaded.path)

  await bucket.remove([uploaded.path])
}
```

Objects are addressed by **path within the bucket**, the same way supabase-js does.
`upload` resolves to `{ path, id, fullPath }`; `download`, `remove`, `createSignedUrl`
and `getPublicUrl` all take that `path`. A bare UUID is also accepted anywhere a path is,
and routes to the object by its server-issued file id instead — useful when you stored the
id rather than the key.

Listing:

```ts
const { data: objects } = await bucket.list('avatars/', {
  limit: 50,
  offset: 0,
  search: 'me',
  sortBy: { column: 'name', order: 'asc' },
})
```

Many files at once:

```ts
const { data: results } = await bucket.uploadMany(
  files.map(file => ({ path: `avatars/${file.name}`, file })),
  {
    concurrency: 4,
    onProgress: ({ completed, total, path, error }) => setProgress(completed / total),
  },
)
```

`uploadMany` never rejects: each entry comes back as `{ path, data, error }`, in input order,
so one bad file does not lose the other nineteen results. `concurrency` defaults to 4, and the
workers share one cursor rather than fixed slices, so a slow file does not stall the rest.

`storage.from(bucket).upload(...)` sends the bucket slug to Motherbase. Quota, CORS, access tokens, and webhooks are still managed from Project Studio, the admin API, or the CLI; buckets themselves can also be administered from the SDK (below).

### Bucket administration

```ts
const { data: buckets } = await client.storage.listBuckets()
const { data: bucket }  = await client.storage.getBucket('avatars')

await client.storage.createBucket('avatars', { public: true, name: 'Avatars' })
await client.storage.updateBucket('avatars', { public: false })

await client.storage.emptyBucket('avatars')             // objects go, bucket stays
await client.storage.deleteBucket('avatars', { force: true })
```

Every one of these needs a **secret** project API key — the same rule Supabase
applies, where bucket administration is a service-role operation. With a
publishable key they resolve with a `401` error, so keep them in server code and
setup scripts, never in a browser bundle. `deleteBucket` refuses a bucket that
still holds objects unless `force` is passed, so one unqualified call cannot
destroy the files in it.

`getPublicUrl(path)` is synchronous and returns `<url>/api/storage/<bucket>/files/<path>`.
Use it only for public bucket objects — it signs nothing and checks nothing. Private
objects should be read with `download()` or `createSignedUrl()` from an authenticated
session.

Copy, move, replace, and metadata:

```ts
await bucket.update('me.png', file)          // upload with upsert forced on
await bucket.copy('me.png', 'archive/me.png', { upsert: true })
await bucket.move('me.png', 'archive/me.png')

const { data: meta } = await bucket.info('me.png')   // no download
const { data: there } = await bucket.exists('me.png')
```

`exists()` reads a `404` as `false`. Anything else — a `403`, a network failure —
comes back as an error rather than as "no", because treating an authorization
failure as absence is how a UI offers to create something that already exists.

Signed URLs, for handing an object to someone without a session (an `<img src>`, an email link). They are signed for the project's storage domain and expire on their own:

```ts
const { data } = await bucket.createSignedUrl('me.png', 900)   // 15 minutes
// data.signedUrl, data.expiresAt

// Several at once. Each entry reports on its own; one missing object does not
// fail the batch.
const { data: many } = await bucket.createSignedUrls(['a.png', 'b.png'], 900)
// [{ path, signedUrl, error }, …]
```

`expiresIn` is in seconds, defaults to `3600`, and must be between `1` and `604800` (7 days,
the AWS SigV4 ceiling). Anything outside that is a `400` rather than a silent clamp — a
caller asking for 30 days wants a 30-day URL, and quietly returning a 7-day one is the same
bug as ignoring the argument.

Direct-to-storage uploads (S3 driver only):

```ts
const { data: slot } = await bucket.createSignedUploadUrl('me.png', {
  size: file.size,
  contentType: file.type,
})

await bucket.uploadToSignedUrl('me.png', slot.token, file)
```

Unlike supabase-js this needs the byte `size` up front: the upload is reserved
against the bucket quota and the signature is bound to that exact length, which is
what stops a signed URL from becoming an unbounded write. `uploadToSignedUrl` PUTs
the bytes and then finalises server-side; the object only becomes readable after
the finalise, so a PUT that lands with a failed finalise leaves a reservation to
expire rather than a half-visible object. The `local` driver has no presigned
uploads.

<Note>
`expiresAt` is `null` when nothing actually expires: a **public** object's URL is permanent,
and a **private** object under the `local` storage driver resolves to the authenticated
streaming endpoint, which is bound to the session rather than to a clock and so cannot be
handed to a third party at all. Check `expiresAt` rather than assuming `expiresIn` applied.
</Note>

## Realtime

```ts
const channel = client
  .channel('room-products')
  .on('postgres_changes', { event: '*', schema: 'public', table: 'products' }, (payload) => {
    console.log(payload.eventType, payload.new, payload.old)
  })
  .subscribe((status, error) => {
    console.log(status, error)
  })

client.getChannels()                 // every channel this client holds
await client.removeChannel(channel)
await client.removeAllChannels()
```

Realtime uses Socket.IO at `/ws`. `socket.io-client` is imported lazily when `connect()` runs, so apps that never use realtime do not need the optional dependency.

Supported channel event types: `postgres_changes`, `broadcast`, `presence`. Any other type
throws immediately rather than silently never firing.

`postgres_changes` event filters: `INSERT`, `UPDATE`, `DELETE`, `*`.

Broadcast:

```ts
const room = client.channel('room-1', { config: { broadcast: { self: true, ack: true } } })

room.on('broadcast', { event: 'cursor' }, ({ payload }) => console.log(payload))
room.subscribe()

await room.send({ type: 'broadcast', event: 'cursor', payload: { x: 12, y: 40 } })
```

The sender receives its own message only with `config.broadcast.self`. With
`config.broadcast.ack`, `send()` resolves on the server ack (`'ok' | 'timed out' | 'error'`)
instead of resolving immediately.

Presence:

```ts
const room = client.channel('room-1', { config: { presence: { key: userId } } })

room.on('presence', { event: 'sync' }, () => console.log(room.presenceState()))
// Each event's callback is typed with its own payload (since 2.2.2)
room.on('presence', { event: 'join' }, ({ key, newPresences }) => console.log(key, newPresences))
room.on('presence', { event: 'leave' }, ({ key, leftPresences }) => console.log(key, leftPresences))

room.subscribe(status => {
  if (status === 'SUBSCRIBED') void room.track({ name: 'Ada', typing: false })
})

await room.untrack()
```

The server sends the full presence state; the client diffs it into `sync` / `join` / `leave`.

`subscribe()` returns the channel, not a promise — `track()` and `send()` before the join ack
are rejected server-side, so issue the first one from the `SUBSCRIBED` callback. See
[Realtime](/docs/platform/realtime) for presence keys, typing indicators, and reconnection.

Channel status, reported to the `subscribe()` callback: `SUBSCRIBED`, `TIMED_OUT`,
`CHANNEL_ERROR`, `CLOSED`.

Payload shape:

```ts
interface PostgresChangePayload<T> {
  schema: string
  table: string
  eventType: 'INSERT' | 'UPDATE' | 'DELETE'
  new: T | Record<string, never>
  old: T | Record<string, never>
  commit_timestamp: string
}
```

Realtime table events respect the same RLS visibility model as REST for rows that still exist. Delete events carry the deleted row in `old`.

The low-level `client.realtime` module is exported for direct table watchers and status listeners, but app code should prefer `client.channel()`.

## Edge functions

```ts
const { data, error } = await client.functions.invoke('hello', {
  body: { name: 'Ada' },
  method: 'POST',        // GET and DELETE send no body
  headers: { 'x-trace': '1' },
})
```

`invoke` always resolves `{ data, error }` — it never throws — but `error` is an
instance of the supabase-js error classes, so ported code that branches on them
keeps working:

```ts
import { FunctionsHttpError, FunctionsFetchError } from '@motherbase/client'

if (error instanceof FunctionsHttpError) console.error(error.status)
```

`FunctionsHttpError` means the function ran and answered non-2xx;
`FunctionsFetchError` means the request never reached it. `FunctionsRelayError` and
the `FunctionsError` base are exported for parity.

Invocation is private by default: a signed-in session is enough, anonymous callers reach
only a function marked **Public** in Studio (see
[Who can call a function](/docs/platform/edge-functions/#who-can-call-a-function)). From a
trusted server with no user, create the client with a **secret** project key: it is sent
with every request, function calls included.

```ts
const server = createClient(process.env.MOTHERBASE_URL!, process.env.MOTHERBASE_SECRET_KEY!)
await server.functions.invoke('hello', { body: {} })
```

A project that uses `EDGE_INVOKE_TOKEN` instead passes it per call:

```ts
await client.functions.invoke('hello', {
  body: {},
  auth: { type: 'edge-token', token: process.env.EDGE_INVOKE_TOKEN! },
})
```

## Subpath exports

Two extra entry points ship in the same package. Neither is loaded by `@motherbase/client` itself.

### `@motherbase/client/query`

Cache keys and fetchers for React Query or SWR. No dependency on either: the returned object
is a plain `{ queryKey, queryFn }`, which is what `useQuery` takes, and SWR uses the same two
fields as key and fetcher.

```ts
import { keys, listQuery, rowQuery, allRowsQuery } from '@motherbase/client/query'

useQuery(listQuery(client, 'posts', {
  filters: { author },
  build: q => q.select('*').eq('author', author).order('created_at'),
}))

useQuery(rowQuery(client, 'posts', id))            // resolves null when absent, does not throw
useQuery(allRowsQuery(client, 'tags'))             // walks stream(), ignores api.rest.maxRows
```

The fetchers **throw** on `{ error }` instead of returning it. That is the whole point: a fetcher
that resolves with `{ data: null, error }` looks successful to React Query, so the error gets
cached, `isError` stays false, and the UI renders an empty list forever.

Keys are hierarchical — `keys.table('posts')` is a prefix of every list and row key below it, so
one `invalidateQueries` after a write reaches all of them. Pass `filters` for any filtered list, or
two different filters on the same table share one cache entry.

### `@motherbase/client/testing`

Run a query as a specific user, or as nobody, so an RLS policy can actually be asserted.

```ts
import { createTestClient } from '@motherbase/client/testing'

const asAlice = createTestClient(url, secretKey, { as: alice.id })
const asBob   = createTestClient(url, secretKey, { as: bob.id })
const asAnon  = createTestClient(url, secretKey, { as: 'anon' })

expect((await asAlice.from('notes').select('*')).data).toHaveLength(1)
expect((await asBob.from('notes').select('*')).data).toHaveLength(0)
```

`as` takes a user id, `'anon'` for a signed-out visitor, or `'service_role'` to keep the secret
key's own bypass-everything identity. Each client gets its own in-memory session, so two of them
in one file cannot clobber each other.

<Warning>
Server side only. It needs the project **secret** key, which bypasses RLS and must never reach a
browser. `createTestClient` throws if the key is not an `mb_secret_…` one, and the server refuses
the `x-motherbase-impersonate` header with a 403 for any other key — so the worst case is a failed
request, not a privilege escalation. Impersonation can only ever lower the privilege of a caller
who already had everything.
</Warning>
