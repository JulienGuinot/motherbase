Any insert, update or delete made through the REST API (`client.from(...)`) can fan out to HTTP endpoints you register. Matching, delivery and the audit trail live in `apps/server/services/events/event-dispatcher.service.ts`.

<Warning>
Row events come from REST writes only, as for [Realtime](/docs/platform/realtime/). A row written by a trigger, inside an
`rpc()` function, by a `pg_cron` job, from the SQL editor or over a direct connection fires no webhook. When a receiver
depends on those rows, make the write through the REST API.
</Warning>

## Event names

```text
<model>.<action>      e.g. todos.created, profiles.updated, orders.deleted
```

`action` is `created`, `updated` or `deleted`. Model names are lowercased.

## Subscription patterns

A webhook stores an `events[]` array. Each entry is matched against the event:

| Spec | Matches |
|---|---|
| `*` | Everything |
| `todos.created` | Exactly that event |
| `todos.*` | Every action on `todos` |
| `*.deleted` | Deletes on any table |

Empty or blank specs never match. Matching is case-insensitive.

### Events that are not row changes

The server also publishes system events, subscribable by the same specs:

| Spec | Fires on |
|---|---|
| `auth.sign-in`, `auth.sign-up`, `auth.sign-out` | the matching auth flow |
| `auth.forget-password`, `auth.reset-password`, `auth.verify-email`, `auth.two-factor` | the matching auth flow |
| `job_alert.created` | a scheduled job failed repeatedly, stopped running, or a backup fell past its objective |

`GET /api/admin/webhooks/events` serves this list, so the Studio picker reads it from the server
that emits them rather than keeping its own copy.

## Delivery

For each affected row, one `POST` per matching enabled webhook:

```json
{
  "event": "todos.created",
  "model": "todos",
  "action": "created",
  "record": { "id": 1, "title": "…" },
  "occurredAt": "2025-01-01T00:00:00.000Z"
}
```

`Content-Type: application/json`, 8 s timeout (`helpers/webhook-sender.helper.ts`). Deliveries are fired without blocking the mutation, and a dispatcher failure is logged rather than propagated — a broken endpoint cannot fail your write.

### Signature

Every delivery is signed following [Standard Webhooks](https://www.standardwebhooks.com), so any of that spec's
libraries verifies it. Each webhook has its own secret (`whsec_…`), shown and rotated from the webhook's panel in
Studio (`POST /api/admin/webhooks/:id/rotate-secret`). Three headers ride along:

| Header | Value |
|---|---|
| `webhook-id` | The delivery id. The same on every retry of one delivery: deduplicate on it. |
| `webhook-timestamp` | Unix seconds when this try was sent. Reject one too far from your clock to stop replays. |
| `webhook-signature` | `v1,` + base64 HMAC-SHA256 of `${webhook-id}.${webhook-timestamp}.${body}`, keyed by the base64-decoded part of the secret after `whsec_`. |

```ts
import { Webhook } from 'standardwebhooks'

const wh = new Webhook(process.env.MOTHERBASE_WEBHOOK_SECRET) // 'whsec_…'
const event = wh.verify(rawBody, headers) // throws when the signature or timestamp is wrong
```

Verify against the raw body, before any JSON parsing. Rotating the secret takes effect at once: the old one stops
verifying, so update the receiver first, or accept both while you switch.

### Retries

A try that fails with a network error, a timeout, `408`, `425`, `429` or any `5xx` is retried after 5 s, 30 s, 2 min
and 8 min: five tries in all over about eleven minutes, with the same `webhook-id`. Any other `4xx` is the receiver
refusing the request and is not retried. Each retry re-reads the webhook, so it stops once the webhook is disabled or
deleted, and it follows a new URL or secret.

Retries wait in the server process. A restart drops the ones still waiting; the delivery log shows the last try that
ran. At most 1000 retries wait at once across the project; past that, a failure is recorded and not retried.

## Delivery log

Every try writes a `WebhookDelivery` row: `event`, `status`, `ok`, `durationMs`, `test`, `errorMessage`, and `attempt` (1 for the first try, 2 for the first retry, and so on). Because that table is only visible from the webhook detail screen, each attempt **also** writes one line into the shared log stream with `source: 'webhook'`:

```text
[webhook] todos.created → https://example.com/hook 200 in 84ms
[webhook] todos.created → https://example.com/hook failed, HTTP 502, retrying in 5s
```

So a failing endpoint is readable in **Logs**, right next to whatever triggered it.

## The outbound HTTP client

Every outbound call the project makes on operator-supplied URLs goes through `services/http/outbound-http-client.service.ts`, which is deliberately not `fetch`:

| Control | Default |
|---|---|
| Timeout | 5000 ms (webhooks pass 8000) |
| Max response size | 256 KB |
| DNS resolution | `helpers/ssrf.helper.ts` — resolves the hostname and rejects private, loopback, link-local, CGNAT, multicast and reserved ranges (IPv4 and IPv6) |
| Connection | **Pinned to the resolved address**, so a re-resolution between check and connect cannot swap in an internal host |

<Warning>
This is what stops a webhook URL from being used to reach `169.254.169.254`, `127.0.0.1`, or anything on your internal network. Do not bypass it by calling `fetch` directly from new code that takes a URL from settings or the database.
</Warning>

Twilio SMS is the deliberate exception (`services/sms.service.ts`): its scheme and hostname are constants and the only interpolated segment is percent-encoded, so it cannot be redirected to an internal host.

## Bucket webhooks

Storage has its own per-bucket hooks (`BucketWebhook`: `url` + `events[]` + `secret`), configured per bucket rather than globally. They are signed and retried exactly as above; their tries go to the log stream, not to the delivery log. See [Storage](/docs/platform/storage/).

## Auth event webhook

Auth emits its own webhook, configured in the `auth.hooks.events` settings group with a signing secret, plus a `auth.hooks.signUp` gate that can refuse a sign-up and a `auth.hooks.send` override for delivery. See [Auth](/docs/platform/auth/) and the [settings reference](/docs/reference/settings/).

## Realtime is a different path

Webhooks are outbound HTTP. Realtime is a WebSocket fan-out with its own transactional outbox (`RealtimeOutbox`) — see [Realtime](/docs/platform/realtime/) and the [data model](/docs/architecture/data-model/).
