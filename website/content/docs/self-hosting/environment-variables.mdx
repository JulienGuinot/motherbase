This page describes where deployment values enter the system and which process consumes them. For application behavior and Project Studio fallbacks, see the [Environment reference](/docs/reference/environment).

<Note>
`deploy/docker-compose.prod.yml` uses an explicit `environment` block, not `env_file`. A variable supported by `apps/server/config/env.ts` is not available inside a production project unless that Compose file forwards it. Console-managed settings can override many application fallbacks without changing Compose.
</Note>

### The `edge-runtime` service

`deploy/docker-compose.prod.yml` runs the Deno sidecar as its own service on its own
network, with no route to Postgres or MinIO — the first of the two barriers that keep a
function away from the stack's internals.

| Name | Consumed by | Required? | Default | Description |
|------|-------------|-----------|---------|-------------|
| `EDGE_RUNTIME_PORT` | `edge-runtime` | no | `9000` | Port the sidecar listens on. |
| `EDGE_RUNTIME_TOKEN` | `edge-runtime` | prod: yes | none | Must match the API's. |
| `EDGE_ALLOWED_INTERNAL_ORIGINS` | `edge-runtime` | no | `http://api:5001` in production Compose | Exact origins a function's `fetch` may call despite resolving to a private address. |
| `DENO_DIR` | `edge-runtime` | no | `/tmp/deno-dir` | Module cache for the worker processes. |
| `EDGE_RUNTIME_IMAGE` | `edge-runtime` service | no | `motherbase-edge-runtime:1.0.0` | Sidecar image. |
| `EDGE_RUNTIME_CPUS` | Compose | no | `0.5` | Sidecar CPU limit. |
| `EDGE_RUNTIME_MEM` | Compose | no | `768M` | Sidecar memory limit. |

Worker-pool tuning (`EDGE_MAX_WORKERS`, `EDGE_WORKER_IDLE_TTL_MS`,
`EDGE_WORKER_MAX_INVOCATIONS`, `EDGE_WORKER_BASE_RSS_MB`) is read by the sidecar too and
documented in the [environment reference](/docs/reference/environment/#the-runtime-sidecar).

## Optional GitHub VPS workflow

The `deploy-vps` job in `.github/workflows/ci.yml` uses:

| Name | Required? | Default | Use |
|------|-----------|---------|-----|
| `VPS_HOST` | deployment: yes | none | SSH host; empty skips deployment. |
| `VPS_SSH_KEY` | deployment: yes | none | SSH private key; empty skips deployment. |
| `VPS_KNOWN_HOSTS` | no | generated with `ssh-keyscan` | Pinned SSH host keys. |
| `VPS_USER` | yes | `motherbase` | Dedicated non-root deploy account; `root` is rejected. |
| `VPS_SSH_PORT` | no | `22` | SSH port. |
| `VPS_REMOTE_DIR` | no | `boilerplate-backend` under the user's home | Remote checkout. |
| `CONSOLE_URL` | smoke test: yes | none | Enables the VPS smoke test when present. |
| `ADMIN_EMAIL` | smoke test: conditional | none | Console smoke-test login. |
| `ADMIN_PASSWORD` | smoke test: conditional | none | Console smoke-test password. |
| `PROJECT` | no | `test` | Smoke-test project. |
| `PROJECT_URL` | critical flows: yes | none | Project API URL. |
| `PROJECT_EMAIL` | critical flows: yes | none | Project test user. |
| `PROJECT_PASSWORD` | critical flows: yes | none | Project test password. |
| `RLS_MODEL` | critical flows: yes | none | Model used by the RLS smoke flow. |
| `PRIVATE_EDGE_ROUTE` | critical flows: yes | none | Private edge route used by the smoke flow. |

The workflow pulls with `--ff-only` and runs `./setup.sh --yes --skip-dns-check` on the VPS. It does not pass `--prod`; the existing non-local `BASE_HOST` makes setup recover VPS mode.
