# Contributing to the website

`website/` is the marketing site and documentation for
[Motherbase](https://www.motherbase.site). The repository-wide rules are in
[../CONTRIBUTING.md](../CONTRIBUTING.md); this file covers the site only.

## Setup

```bash
cd website
npm install
cp .env.example .env.local
npm run dev          # http://localhost:3000
```

Node 22 or newer.

## Before opening a pull request

```bash
npm run lint
npx tsc --noEmit
npm test
npm run build
```

CI runs exactly these four. A pull request that fails them will not be reviewed
until it is green.

## Editing documentation

Docs are MDX files under `content/docs/<section>/<page>.mdx`. Each needs
frontmatter:

```mdx
---
title: Page title
description: One sentence, used for the meta description and search.
order: 3
---
```

`order` positions the page inside its sidebar group; the sidebar is derived from
frontmatter in `lib/nav.ts`, so there is no separate navigation file to update.
A new section directory needs one entry in the group list in `lib/nav.ts`.

Write documentation that matches the shipped behaviour. If a doc and the code
disagree, the code is right: fix the doc in the same pull request, and open an
issue if the behaviour itself looks wrong.

Five blocks are **generated** and must not be hand-edited. All are written by the
backend (the parent directory) and only copied here by `npm run docs:sync`, which
`lib/__tests__/sync-backend-docs.test.ts` fails on when any of them is stale:

| Where | Generated by |
|---|---|
| The route table in `content/docs/reference/admin-api.mdx`, between the `BEGIN/END GENERATED ROUTES` markers | `npm run docs:routes` at the repository root writes `docs/admin-routes.md` from the controller decorators |
| The compatibility matrix in `content/docs/reference/sdk.mdx`, between the `BEGIN/END GENERATED COMPATIBILITY` markers | the `sdk-contract` test writes `packages/client/COMPATIBILITY.md` by running the real client against a real server |
| The command table in `content/docs/cli/commands.mdx`, between the `BEGIN/END GENERATED CLI` markers | `npm run docs:cli` at the repository root writes `docs/cli-commands.md` from the command registry |
| The command summary in `content/docs/cli/overview.mdx`, between the `BEGIN/END GENERATED CLI OVERVIEW` markers | the same `docs/cli-commands.md`, one row per command with its subcommands |
| The settings tables in `content/docs/reference/settings.mdx`, between the `BEGIN/END GENERATED SETTINGS` markers | `npm run docs:settings` at the repository root writes `docs/settings.md` from the settings registry |

Editing any of them by hand is reverted by the next sync, and a claim typed
into one is a claim no test backs.

`lib/__tests__/mdx-safety.test.ts` covers the one failure mode no other suite used
to catch: MDX parses JSX and JS expressions in prose, so a bare `<name>`
or `createClient<Database>` is an unclosed tag, and a bare `{ auth: { persistSession } }`
is an expression acorn rejects. Both fail only in `next build`. Put angle brackets
and braces in backticks, and register a new component in `app/docs/[...slug]/page.tsx`
before a page uses it. The sync escapes both in the generated blocks
(`escapeMdxSyntax`), so this rule is yours to keep in hand-written prose.

## Conventions

- TypeScript, no `any` in new code.
- Server Components by default; add `"use client"` only where interactivity
  requires it.
- Tailwind v4 utilities for one-off styling, CSS Modules for component-scoped
  styles — follow whichever the neighbouring component already uses.
- Commit messages follow Conventional Commits (`docs:`, `fix:`, `feat:`).

## Reporting problems

Open an issue with the page URL and what is wrong or missing. Typos and broken
links are welcome as pull requests directly, no issue needed.
